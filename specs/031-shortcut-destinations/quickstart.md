# Verification guide

Use isolated temporary service data and controlled provider/transport boundaries. Never edit the running account's shortcuts or post to arbitrary channels. Record exact test names and receipts in docs/reports/shortcut-destinations.md.

1. Save a destination via existing shortcut service/CLI boundaries, reload disk and compare; reject invalid nested data/old host field loss. Legacy no-destination run follows its previous path.
2. Admit two runs, change shortcut destination between them, complete source work and verify snapshot-specific distinct native threads. Inject duplicate completion and restart states; known receipts do not republish.
3. Inject an authorized Discord thread message without mention through the real module event path. Inspect real Manager inbox/backing session and original worker notes; continue through controlled provider. Unauthorized/cross-thread replies fail.
4. Manager-target runs must stay unpublished during enqueue, acknowledgment, delegated work, open approval, active goal/queue/background task. Publish after actual completion; preserve isolated context after reload.
5. Exercise missing/disabled destination, permission refusal, ambiguous send, cleaned output, long result and deleted source context. Failure does not become success or a different destination.
6. Mount actual desktop/phone shortcut components. Review 1280x900 and 390x844 light/dark; normal clicks, keyboard/focus, scroll, save/reopen, cancel, error and long labels. Mock save proves UI only.
7. Run focused tests, client typecheck/lint/full suite, desktop/service build without replacing active out/service, mobile build and performance review. Preserve baseline failures with evidence.
8. Live check, only when a project-provided safe channel/account is identified: complete two harmless runs to that exact destination; inspect native receipts and reply in each thread through real Manager. If none exists, document channel ID/permissions/setup needed without making a post or claiming live delivery.
