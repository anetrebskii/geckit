# Team direct messages
The existing topic connection gains Team direct messages, initially disabled. Owner chooses allowed projects (empty initially), enables DMs, creates invitations, confirms the displayed numeric identity, and revokes members. Each member can optionally approve only their own scoped decisions. Group approvers cannot see private decisions. The owner can inspect all data locally.
States: disabled, enabled/empty, invitation pending, candidate awaiting confirmation, admitted, revoked, waiting for Manager, waiting for worker, waiting for approval, delivery uncertain, storage error. An invitation lasts ten minutes; expired/cancelled candidates never gain access. Revocation is immediate; stopping an already running provider may fail and must be visible.
Use existing settings fields/buttons and token-based styles. Show shared-computer access and absence of OS isolation before enabling. Focus stays on enabled controls after actions; Escape cancels an invitation, not the connection. Long member lists scroll, IDs and long project paths wrap. Narrow and wide/light/dark previews use the real ManagerTelegram component at client/test/browser/team-telegram.
A private reply is never redirected to the topic. Slow files/turns block only their own route. Status explains the actual wait. Old links/buttons request fresh instructions. No automatic publishing of private work.

## Admission and scope
The existing topic connection remains the only bot connection. Its owner controls are desktop-only; the phone view omits member administration. Enabling starts with no allowed projects. Only registered projects explicitly listed here are available; a participant can receive a narrower subset. Create an invitation, send its one-use link, then check and confirm the numeric Telegram identity shown locally. The link alone never grants access. Changing the common project list or disabling DMs revokes all existing private routes; fresh invitations are required.

Participants manage only their own route's tasks and files. Topic approvers do not gain private access. The installation owner manages admission, approvals without delegated permission, global history and Manager configuration. A private member or topic cannot stop the installation-wide Manager or operate personal channels. Confirmation buttons belong to their exact route, decision and Telegram message. Revocation is persisted before stopping work; any unconfirmed stop displays the affected session IDs. An old reply cannot move into a newly admitted chat or topic.

## Waiting and limits
Within one private conversation, messages keep their order. Different conversations can prepare up to four inputs and run up to four Manager turns concurrently. Native workers permit two running workers per private route and four for the topic, still subject to the installation's existing worker limit. A slow file or provider in one route leaves others usable. Status reports the route's wait; queued work is not silently dropped.

Private routes accept 32 unfinished requests and the topic 100, with 256 global output reservations. Overflow is rejected before file download or worker launch. Transport handoff holds 512 updates/16 MiB; a full journal stops advancing its offset until capacity is available. Files are at most 20 MiB each, 32/40 MiB per restricted route and 256/200 MiB globally; unpinned files expire after 24 hours. Active references are protected. Reply links are bounded to 2048 globally and 128 per DM; exhausted active storage refuses a new send. Invitations are limited to 16, active members to 32 plus the explicit owner route, and retained member bindings to 1024. Full archived storage asks the owner to clear the corresponding local history before readmission. Uncertain sends are shown and never automatically repeated.

The visible settings support is implemented in the working tree. Installed-app rollout and live Telegram validation require separate authorization.
